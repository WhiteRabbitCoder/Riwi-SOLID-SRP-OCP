01 · Antes de SOLID

Un objeto reúne datos y operaciones que pertenecen al mismo concepto.

En una tienda, Product, Order y Payment describen conceptos distintos del problema.

Clase = molde. Objeto = instancia concreta.

Product laptop = new Product("Laptop", 3_000_000);
laptop.calculatePriceWithTax();

02 · El contrato permite variar el comportamiento

La interfaz expresa qué debe poder hacerse; cada clase decide cómo hacerlo.

interface Animal { void makeSound(); }

class Dog implements Animal { public void makeSound() { ... } }
class Cat implements Animal { public void makeSound() { ... } }

Animal pet = new Dog(); // el contrato no cambia
pet.makeSound(); // la implementación sí

Programar contra un contrato prepara el terreno para OCP. No es un fin en sí mismo.

El problema de diseño

Que compile no significa que sea fácil de cambiar.

Demasiadas tareas

Una clase calcula, guarda, envía y genera archivos.

Demasiadas variantes

Un método crece con cada nuevo if o else.

La pregunta útil

¿Qué cambio futuro obligaría a editar este archivo?

SOLID ayuda a elegir fronteras para que el cambio sea local y explicable.

03 · S — Single Responsibility Principle
S

Una clase debería tener una sola razón para cambiar.

No significa “una clase por método”. Significa que sus métodos sirven a una responsabilidad coherente.

Señal de alerta: describes la clase usando muchos “y”.

docs/04-srp.mdCLASE / 06
SRP · Diagnóstico guiado

InvoiceService concentra decisiones que evolucionan por separado.

class InvoiceService {
  calculateTotal(); // reglas de cálculo
  saveInvoice(); // persistencia
  sendInvoiceByEmail(); // proveedor de correo
  generatePdf(); // formato / librería
}

Cuatro cambios posibles; un solo archivo que recibiría todos los golpes.

04 · O — Open/Closed Principle
O

Abierto a extensión; cerrado a modificación innecesaria.

Cuando esperamos variantes reales, definimos un punto estable y agregamos implementaciones alrededor de él.

OCP no significa “nunca modificar código”. Significa evitar reescribir el núcleo por cada variante previsible.

OCP · El patrón que avisa

Si cada medio de pago agrega otra condición, el coordinador conoce demasiado.

void processPayment(String type, double amount) {
  if ("CARD".equals(type)) { ... }
  else if ("CASH".equals(type)) { ... }
  else if ("BANK_TRANSFER".equals(type)) { ... }
  // ¿Nequi? editar de nuevo este método.
}

El problema no es el if aislado: es que las nuevas variantes siempre obligan a tocarlo.

exercises/ocp/ex02/PaymentService.javaCLASE / 12
OCP · Diseñar el punto de extensión

PaymentService coordina el contrato; cada forma de pago implementa su comportamiento.

interface PaymentMethod { void pay(double amount); }

class CreditCardPayment implements PaymentMethod { ... }
class CashPayment implements PaymentMethod { ... }
class NequiPayment implements PaymentMethod { ... }

paymentMethod.pay(amount); // coordinador estable

docs/08-reto-final.mdCLASE / 15
Criterio de entrega

Una buena solución explica sus límites, no solo acumula clases.

Para SRP

  • ¿Qué responsabilidad tiene cada clase?
  • ¿Por qué podría cambiar?
  • ¿La separación mejora el flujo?

Para OCP

  • ¿Qué comportamiento puede variar?
  • ¿La nueva variante evita editar el núcleo?
  • ¿La abstracción aporta algo real?

Incluye dos configuraciones del reto y una decisión que deliberadamente no abstrajiste.
